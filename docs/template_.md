# R&S Entertainment 오락기기 자산 추적·관리 시스템

## 1. 프로젝트 개요

- **프로젝트명**: R&S Entertainment Amusement Machine Asset Tracking & Management System
- **유형**: 데이터베이스 설계 및 웹 기반 자산관리 시스템 구현 팀 프로젝트
- **저장소**: [GitHub Repository](https://github.com/jkshin0903/maria-streamlit-app)
- **목표**: 종이·수기 중심의 오락기기 자산 관리 업무를 디지털화하여 구매, 입고, 창고 보관, 설치·이동·제거, 수리, 처분 및 성과 분석을 하나의 흐름으로 관리하는 시스템을 구현했다.

R&S Entertainment Services의 핀볼, 당구대, 주크박스, 비디오 게임 자산을 대상으로 했다. 사용자가 **현재 어떤 장비를 얼마나 보유하고 있는지, 어느 사업장에 설치되어 있는지, 수익성과 수리 부담은 어떤지** 즉시 확인할 수 있도록 데이터 모델과 웹 UI를 설계·구현했다.

## 2. 문제 정의와 해결 방향

기존 업무는 구매 주문, 장비 이동, 설치 이력, 수리 정보, 사업장 계약 정보가 종이 문서와 수작업에 분산되어 있어 재고·위치·상태를 즉시 파악하기 어려웠다. 이에 다음 문제를 해결하는 것을 우선순위로 두었다.

1. **자산 추적성 확보**: 제품 단위(Product)와 실제 물리 자산 단위(Machine, Serial Number)를 분리하여 개별 장비의 구매부터 처분까지 추적한다.
2. **업무 흐름의 연결**: 구매발주(PO) → 송장(Invoice) → 개별 장비 등록 → 설치·이동 오더 → 위치 이력 → 수익·수리 분석으로 이어지는 데이터 흐름을 설계한다.
3. **의사결정 지원**: 단순 조회를 넘어 수익, R&S 수익 배분율, 수리 횟수·비용, 과거 설치 이력을 함께 분석해 이전·교체·폐기 판단을 돕는다.
4. **운영 접근성 강화**: 개인 데스크톱과 교내 네트워크에 의존하던 개발 환경을 클라우드로 이전하여, 장소에 제약 없이 협업·검증 가능한 운영 환경을 구성한다.

## 3. 수행 내용

### 3-1. 요구사항 분석 및 데이터 모델링

- 화면 기능 정의서와 시스템 목표를 기준으로 구매, 송장, 기기, 사업장, 계약, 이동 지시, 수리, 수익 데이터를 핵심 도메인으로 정리했다.
- `business_location`, `contract`, `machine`, `machine_contract_hst`, `order`, `technician`, `vendor`, `product`, `purchase_request`, `purchase_order`, `invoice` 등 핵심 엔터티를 도출하고 관계형 모델로 매핑했다.
- 구매발주–제품, 송장–제품의 다대다 관계를 각각 상세 테이블로 분리했으며, 장비와 계약의 이력 관계를 별도 이력 테이블로 모델링했다.
- 초기 DDL 모델을 웹 애플리케이션 요구사항에 맞게 확장했다. 제품 제조사·기기유형·가격, 장비 구매/설치/처분 정보, 계약별 수익 배분율, 이동 일정·서명·메모를 추가하고, `machine_repair`, `machine_revenue`, `machine_location_hst` 테이블을 구현했다.
- `seed.py`를 통해 누락된 스키마를 추가하고, 재현 가능한 샘플 데이터를 적재하는 멱등성 데이터 시딩 구조를 구성했다.

### 3-2. Streamlit 기반 업무 화면 구현

#### 구매발주 입력 화면 — `SCR-IN-01`

- 발주번호 자동 채번, 오늘 날짜 기본 설정, 사용자·벤더 선택, 벤더 연락처 자동 조회 기능을 구현했다.
- 제품 선택 시 제조사·기기 유형·기준 단가를 자동 반영하고, 여러 품목을 동적으로 추가·삭제할 수 있는 발주 라인 편집 UI를 구현했다.
- 수량과 단가를 바탕으로 품목별 합계 및 전체 발주 금액을 계산해 표시했다.
- 벤더 미선택, 품목 미입력, 중복 제품, 수량 오류, 0 이하 단가, 최대 품목 수 초과 등을 검증하여 잘못된 발주 저장을 방지했다.
- 유효성 검증 후 `purchase_order`와 `purchase_order_item`에 발주·상세 품목을 저장하고, 발주 상태를 `Pending`으로 등록했다.
- 벤더 팩스번호 존재 여부를 확인하는 발송 전 검증 흐름을 구현했다. 현재 저장소 코드의 팩스 처리 결과는 UI 시뮬레이션이며, 실제 팩스 API 연동은 범위에 포함하지 않았다.

#### 설치·제거·이동 지시 화면 — `SCR-IN-02`

- 장비 일련번호를 기준으로 현재 위치·상태·기기 유형·제조사와 과거 설치 이력을 조회하는 이동 지시 UI를 구현했다.
- 설치, 제거, 이동 유형에 따라 출발지와 도착지를 구성하고, 지역별 기술자 필터 및 작업 예정 일시를 지원했다.
- 동일 장비의 중복 등록, 동일 출발·도착지 지정, 이미 설치된 위치로의 재설치, 과거 저성과 사업장으로의 재설치 가능성을 사전에 경고했다.
- 한 오더에 여러 장비를 처리하는 다중 라인 구조와 임시저장·제출 상태를 구현했다.
- 기술자 서명과 완료 일시를 입력해 작업 완료를 처리하면 `machine`의 현재 위치·상태·설치일을 갱신하고, `machine_location_hst`에 새 위치 이력을 기록하도록 구현했다.

#### 보고서 화면 — `SCR-RPT-01` ~ `SCR-RPT-03`

- **설치 기기 현황 보고서**: 사업장·기기 유형·상태·설치일 기준으로 설치 자산을 필터링하고, 결과를 Excel로 내보내도록 구현했다.
- **연간 구매 목록 보고서**: 연도, 기간, 벤더, 기기 유형, PO 상태별로 구매 내역을 조회하고, 품목별 단가·수량·합계·수령·처분 정보를 확인할 수 있도록 구성했다.
- **기기 수익성 및 수리 이력 분석 보고서**:
  - 기간별 장비 수익과 사업장 계약의 수익 배분율을 결합해 R&S 수익을 계산했다.
  - 장비별 일평균 수익, 누적 수리 횟수, 누적 수리비, 위치 이력을 함께 조회했다.
  - 성과 임계값 미만 장비를 `Low` 상태로 강조하고, 수익 대비 수리비 비율이 높으면 폐기 권고, 저성과 장비는 이전 권고, 수리 횟수가 많은 장비는 교체 권고를 제시했다.
  - 설치 기간이 짧은 장비와 분석 데이터가 부족한 경우를 별도로 안내해 성급한 성과 판단을 줄였다.
- 공통적으로 다국어 UI, 사용자 역할별 화면 접근·사업장 데이터 범위 제한, Excel 다운로드 기능을 적용했다.

### 3-3. 애플리케이션 구조화 및 안정성 고려

- `lib/`에 DB 접근, UI 공통 요소, 다국어 문자열, Excel 내보내기 로직을 분리하고 `screens/`에 기능별 화면을 분리해 유지보수성을 높였다.
- PyMySQL 기반 DB 접근 계층에서 세션 단위 연결을 관리하고, 연결 오류 발생 시 재연결을 시도하도록 구성했다.
- 벤더·제품·사업장·기술자 등 자주 쓰는 마스터 데이터는 Streamlit 캐시를 적용해 반복 조회 부담을 낮췄다.
- 화면 진입점은 영어 기본 `app.py`, 한국어 기본 `app_ko.py`로 분리하고 공통 앱 부트스트랩을 통해 역할 기반 메뉴를 구성했다.

### 3-4. 클라우드 전환 및 배포 환경 구성

랩실 데스크톱의 전원 불안정과 교외 접속 제한 문제를 해결하기 위해 개발·운영 환경을 클라우드 기반으로 전환했다.

- 기존 MariaDB를 **Aiven**의 클라우드 DB 환경으로 이전해 외부에서도 DB에 접근할 수 있도록 했다.
- Streamlit 애플리케이션을 **Streamlit Cloud**에 배포하고 GitHub 저장소와 연결했다.
- 코드 변경 후 GitHub 반영을 통해 배포 환경에 업데이트가 적용되는 흐름을 구성했다.
- DB 연결 설정은 로컬 `db.ini` 또는 Streamlit Secrets를 우선 사용하도록 설계하고, SSL CA 인증서를 이용한 TLS 연결을 지원하도록 구현했다.
- 이 전환을 통해 특정 PC·교내 네트워크에 종속된 개발 방식을 개선하고, 팀원이 장소와 관계없이 동일한 데이터 및 애플리케이션 환경에서 확인·협업할 수 있게 했다.

## 5. 중요하게 생각한 점

### 5-1. 데이터의 연결성과 추적 가능성

단순히 화면을 여러 개 만드는 것보다, 구매 문서의 품목 정보가 송장과 실제 장비의 일련번호로 이어지고, 장비의 이동·설치 완료가 현재 위치와 이력에 반영되도록 **업무 데이터가 끊기지 않게 연결하는 것**을 중요하게 생각했다. 이를 통해 보고서가 단순 예시 데이터가 아니라 운영 이력에 근거한 의사결정 도구가 되도록 했다.

### 5-2. 현업 사용자가 실수하기 어려운 UX

사용자가 직접 입력해야 하는 값을 줄이고, 벤더·제품·장비·위치를 선택하면 관련 정보가 자동으로 조회되도록 설계했다. 또한 중복 품목, 잘못된 위치 이동, 저성과 장소 재설치, 누락된 필수값 등은 저장 전에 검증·경고해 데이터 품질을 높이는 데 집중했다.

### 5-3. 분석 결과를 행동으로 연결

수익성 보고서에서 매출과 수리 비용만 보여주는 데 그치지 않고 `Keep`, `Relocate`, `Replace`, `Junk`와 같은 추천을 제공했다. 특히 저성과 장비의 과거 위치 이력까지 확인해 이동 지시 화면의 경고와 연결함으로써, 분석 결과가 실제 운영 의사결정으로 이어지도록 설계했다.

### 5-4. 실제로 사용할 수 있는 접근성·운영성

개인 PC의 전원 문제와 교외 접속 제약을 단순한 개발 환경 이슈로 두지 않고, Aiven과 Streamlit Cloud로 전환해 **언제 어디서나 접근 가능한 환경**을 만들었다. GitHub 연동 배포를 통해 코드 변경이 서비스에 반영되는 흐름을 구성한 점은, 기능 구현뿐 아니라 지속적인 운영과 협업 가능성을 함께 고려한 경험이다.

## 6. 자기소개서용 서술 예시

### 6-1. 핵심형

데이터베이스 설계 팀 프로젝트에서 오락기기 자산의 구매·설치·이동·수리·처분 전 과정을 관리하는 웹 시스템을 구현했습니다. MariaDB 기반 ER 모델과 DDL을 설계하고, Streamlit과 PyMySQL로 구매발주·이동 지시·설치 현황·연간 구매·수익성 및 수리 이력 분석 화면을 개발했습니다. 특히 기기별 수익, 계약별 수익 배분율, 수리비, 위치 이력을 결합해 이전·교체·폐기 권고를 제공하도록 설계했습니다. 이후 개인 PC와 교내 네트워크에 종속된 환경의 문제를 해결하기 위해 DB를 Aiven으로 이전하고 Streamlit Cloud에 배포해 외부에서도 접근·협업 가능한 환경을 구축했습니다.

### 6-2. 문제 해결·운영 관점형

프로젝트 진행 중 개발 PC의 전원 불안정과 교외 접속 제한으로 협업 및 검증에 어려움이 있었습니다. 이를 해결하기 위해 MariaDB를 Aiven 관리형 클라우드 DB로 이전하고, Streamlit 애플리케이션을 GitHub 연동 방식으로 Streamlit Cloud에 배포했습니다. 그 결과 특정 장비와 네트워크에 의존하던 환경을 개선했으며, 코드 변경 사항을 원격 환경에 반영하고 팀원이 동일한 시스템에 접속해 확인할 수 있는 개발·운영 흐름을 마련했습니다.

### 6-3. 데이터 모델링·서비스 구현 관점형

종이 기반 자산 관리 업무를 데이터 모델부터 웹 서비스까지 구현했습니다. 제품과 실제 장비를 분리하고, 구매발주·송장·장비·계약·이동오더·위치이력·수리·수익 데이터를 관계형 모델로 설계했습니다. 이후 입력 단계의 유효성 검증과 자동완성, 역할별 접근 범위, 위치 이력 자동 갱신, Excel 보고서 내보내기를 구현해 데이터 정확성과 현업 사용성을 함께 확보했습니다.

## 7. 포트폴리오용 한 줄 요약

**MariaDB 기반 자산 이력 모델을 Streamlit 웹 애플리케이션으로 구현하고, Aiven·Streamlit Cloud·GitHub 연동으로 장소 제약 없이 운영 가능한 오락기기 자산관리 시스템을 구축했습니다.**

## 8. 근거 및 작성 유의사항

- 기능 설명은 제출 문서, UI 기능 정의서, 저장소 코드에서 확인한 범위로 작성했다.
- 클라우드 전환과 배포 환경 구성은 프로젝트 메시지에서 직접 언급한 내용을 반영했다.
- 저장소는 팀 프로젝트이며, 개별 소스 파일의 작성자별 기여도는 제공된 문서와 공개 저장소 화면만으로 확정하기 어렵다. 따라서 자기소개서 제출 시 본인이 직접 담당한 모듈·역할이 명확하다면 위 문장에서 `팀과 함께 구현`을 `주도하여 구현` 또는 실제 담당 범위로 조정한다.
