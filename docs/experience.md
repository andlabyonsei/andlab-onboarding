## 한 줄 요약

> 연구용 공용 Linux 서버 2대를 운영하며, Milvus OOM과 루트 파티션 포화 사례를 분석해 계정·저장공간·리소스 사용 기준을 수립하고, 이를 재현 가능한 온보딩 문서와 점검 스크립트로 표준화했습니다.

## 기본 정보

- 기간: 2025.05 ~ 2026.07 (문서화·운영 이력 기준)
- 소속/상황: ANDlab 연구용 공용 Linux 서버 운영 및 신입 랩원 온보딩
- 역할: 공용 서버 운영 지침 정리, 장애 원인 분석 지원, 하드웨어 점검·계정 환경 표준화, 운영 지식 문서화
- 함께한 사람: 랩장, 서버 관리자, 연구용 서버를 사용하는 랩원
- 관련 직무: Linux 시스템 운영, 인프라 운영, MLOps/AI 플랫폼 운영, 기술 문서화
- 사용한 기술 또는 도구: Ubuntu, SSH, Bash, Docker Compose, NVIDIA GPU(`nvidia-smi`), Milvus, Conda, PyTorch, `htop`, `glances`, `free`, `df`, `du`, `ps`, `dmidecode`, Git/Markdown

## 상황

어떤 배경이나 문제가 있었는가?

- GPU 학습, 대규모 실험, Milvus 벡터 DB를 여러 랩원이 공용 서버에서 동시에 사용했다. 개인 실험 환경의 설정과 자원 사용 방식이 제각각이어서, 한 사람의 작업이 다른 사용자의 SSH 접속·실험·서비스에 영향을 줄 수 있었다.
- 2025년 5월 Milvus 재기동 과정에서 서비스가 반복적으로 중단되고 SSH와 일반 명령 실행도 느려지는 문제가 발생했다. 조사 결과 Docker 또는 GPU VRAM 문제가 아니라, collection 로드에 약 200GB의 시스템 RAM이 필요한 상태에서 다른 실험이 메모리를 점유해 발생한 OOM이었다.
- 2026년 3월에는 OS가 설치된 루트 파티션이 거의 100%에 도달했다. 전체 약 1.8TB 중 `/home`이 약 1.5TB를 사용하고 있었으며, 가상환경·모델 캐시·체크포인트·실험 로그가 개인 홈 디렉터리에 누적된 것이 핵심 원인이었다.
- 2026년 6월 RAM 재배치·증설과 불량 모듈 교체가 진행되었고, 7월에는 과도한 병렬 세션으로 시스템 공용 자원이 소진되어 `sudo`가 실패할 수 있는 문제도 확인되었다. 개별 장애 대응뿐 아니라 지속 가능한 사용 규칙과 신규 구성원 교육이 필요했다.

## 과제

내가 맡은 책임과 해결해야 했던 과제는 무엇이었는가?

- CPU·RAM·GPU·디스크·세션처럼 서로 영향을 주는 공용 자원의 상태를 확인하고, 장애 원인을 사용자에게 설명 가능한 운영 기준으로 바꾼다.
- 신규 랩원이 SSH 접속부터 CUDA/PyTorch 환경 구성, 저장공간·캐시 설정, GPU 사용까지 안전하게 수행하도록 온보딩 경로를 만든다.
- 운영 지식을 특정 관리자 개인의 기억에 의존하지 않도록 문서·스크립트·공지 이력으로 남기고, 장애 재발을 예방한다.

## 행동

내가 실제로 한 일을 구체적으로 작성한다.

### 내가 한 일

- 공용 서버 2대의 역할, GPU·저장공간 사용 원칙, 대규모 작업 사전 공유, 서버 간 작업 분산 규칙을 한 개의 서버 개요 문서로 정리했다.
- 계정 생성 절차, 교외 접속을 위한 VPN, SSH config, VS Code/Cursor Remote SSH 연결, 신규 계정의 기본 용량 제한(최대 100GB)을 단계별 가이드로 작성했다.
- 루트 파티션 포화 사례를 바탕으로 대용량 데이터·Conda 가상환경·Hugging Face/PyTorch/pip 캐시·체크포인트·실험 로그를 `/home`이 아니라 `/mnt`에 저장하도록 기준을 수립했다.
  - `HF_HOME`, `TORCH_HOME`, `PIP_CACHE_DIR`을 사용자별 `/mnt` 경로로 지정하는 `.bashrc` 예시를 제공했다.
  - `OMP_NUM_THREADS=8`, `MKL_NUM_THREADS=8`, `TOKENIZERS_PARALLELISM=false` 설정으로 개인 실험이 CPU 스레드를 과도하게 점유하지 않도록 안내했다.
  - 루트 파티션은 최소 300~400GB(약 20%)의 여유 공간을 유지해야 한다는 운영 목표와, `conda clean`, 캐시·오래된 checkpoint·로그 정리 절차를 문서화했다.
- Milvus OOM 사례를 Docker·GPU 문제로 단정하지 않고 시스템 RAM 관점에서 설명했다. `free -h`, `htop`, `glances`, `nvidia-smi`로 CPU·RAM·GPU를 함께 점검하도록 작업 전후 체크리스트를 만들었다.
- Milvus의 Docker Compose 기동·종료, Attu를 통한 collection 상태 확인, 설정 파일 반영 시 주의사항을 정리하고, collection 로드 전 RAM 여유 확인과 담당자 협의를 필수 절차로 안내했다.
- 반복적인 점검 작업을 줄이기 위해 다음 Bash 스크립트를 작성·공유했다.
  - `ram_info.sh`: `dmidecode` 출력을 파싱해 RAM 슬롯 위치, 용량, 타입, 속도, 제조사와 장착 모듈 수를 표로 표시
  - `collect_sysinfo.sh`: CPU, RAM, 디스크, GPU, OS, 네트워크 정보를 날짜별 파일로 수집
  - `check_disk_usage.sh`: `/home` 및 지정 경로의 용량을 조회해 CSV 보고서로 저장
  - `gpu_users.sh`: GPU별 PID·사용자·프로세스·VRAM 점유량과 비율을 표시
  - `top_mem_procs.sh`: 메모리 점유 상위 프로세스와 계정별 RAM 사용량 합계를 표시
  - `check_accounts_permissions.sh`: UID 1000 이상 계정의 그룹 권한을 요약
- RAM 증설·재배치 및 불량 모듈 대응 시 `dmidecode`와 자체 스크립트로 모듈 인식 상태를 점검하고, 구매·설치·정상 동작 확인을 사진과 함께 남겨야 하는 문서화 요구사항도 정리했다.
- 기존 공지 메일을 단순 보관하지 않고 OOM, 디스크 부족, 계정별 용량 관리, 과도한 세션 제한의 배경·영향·행동 지침으로 재구성해 온보딩 문서에서 바로 참조할 수 있도록 했다.

### 문제 해결 과정

- 문제를 어떻게 분석했는가:
  - Milvus 중단 시 GPU VRAM이나 Docker 상태만 보지 않고, `glances`·`free -h`로 전체 시스템 RAM 사용률과 collection 로드 요구량을 확인했다. 약 200GB RAM이 필요한 collection 로드와 동시 사용자 작업이 겹쳐 OOM이 발생했음을 분리했다.
  - 디스크 이슈는 `df -h`로 파일시스템 전체 사용률을, `du -sh /home/* | sort -h`로 계정별 사용량을 확인해 `/home`의 가상환경·캐시·학습 산출물이 루트 파티션을 압박한다는 원인을 구체화했다.
  - 하드웨어 이상은 `sudo dmidecode -t memory`를 통해 슬롯별 인식 상태를 확인하고, 모듈 불량과 메인보드 슬롯 이상을 구분하는 기준을 정리했다.
- 어떤 대안을 비교했는가:
  - 장애 때마다 관리자에게 개별 문의하는 방식과, 사용자가 사전에 리소스를 확인하고 공통 기준을 따르도록 문서·스크립트로 표준화하는 방식을 비교했다.
  - `/home`에 개인 환경을 그대로 유지하는 방식과, OS 영역은 보호하고 사용자별 `/mnt` 경로로 환경·캐시·산출물을 분리하는 방식을 비교했다.
- 왜 이 방법을 선택했는가:
  - 공용 연구 서버는 단일 사용자의 편의보다 전체 서비스 안정성이 중요하다. 명령어 나열만으로는 사용자가 자신의 작업 영향을 판단하기 어렵기 때문에, 실제 장애 사례·위험·점검 명령·해결 행동을 연결한 가이드와 자동화 스크립트를 함께 제공했다.
  - 사용자마다 환경이 달라도 `.bashrc`와 `/mnt/{계정명}`이라는 공통 진입점을 제공하면 신규 계정에도 같은 정책을 반복 적용할 수 있다.
- 실행 과정에서 생긴 어려움과 대응:
  - 서버별로 `/mnt/nvme02`, `/mnt/nvme03` 등 사용 경로가 달랐다. 특정 경로를 절대 규칙으로 강제하지 않고, 원칙은 “대용량은 `/home`이 아닌 배정된 `/mnt`”으로 명시하고 개인별 경로 확인 절차를 추가했다.
  - 명령어 실행에는 `sudo` 권한이 필요한 경우가 있었다. 관리자 전용 점검과 일반 사용자가 할 수 있는 점검을 구분하고, 계정 정보·권한 세부사항은 문서에 기록하지 않도록 보안 경계를 뒀다.
- 다른 사람과 어떻게 협업했는가:
  - 랩장·서버 관리자와 계정 생성, 권한, 하드웨어 교체, Milvus 운영 절차를 구분해 문서화했다.
  - 랩원에게는 대규모 작업 전 공유, GPU 사용 일정 기록, 작업 종료 후 프로세스·세션 정리를 요청해 운영 정보를 양방향으로 수집하도록 했다.

## 결과

가능하면 객관적인 근거와 함께 작성한다.

- 결과:
  - 공용 서버 이용 과정을 개요 → SSH·계정 → 개발 환경 → 디스크·캐시 → 리소스 → Milvus → 명령어·스크립트 → 관리자 유지보수 순서의 온보딩 문서로 구조화했다.
  - RAM OOM, 루트 파티션 포화, RAM 불량, 과도한 세션 등 실제 운영 사례가 원인·영향·대응 원칙과 함께 기록되어 있다.
- 개선된 점:
  - 사용자가 GPU VRAM만 확인하던 관행에서 CPU·시스템 RAM·디스크·남은 프로세스까지 확인하는 사전/사후 점검 흐름으로 확장했다.
  - 신규 계정에 캐시 경로와 CPU 스레드 제한을 기본 적용할 수 있게 되어, 가상환경·캐시가 루트 파티션을 채우는 문제를 예방할 기반을 마련했다.
  - 점검 결과를 터미널 화면에 의존하지 않고 CSV·시스템 정보 파일·표 형태로 남길 수 있게 했다.
- 사용자·팀·조직에 미친 영향:
  - 신규 랩원이 관리자에게 반복 문의하지 않고 SSH 연결, 원격 개발, CUDA/PyTorch 확인, 저장공간 정책을 스스로 따라갈 수 있는 공통 진입점을 제공했다.
  - 운영 정책의 이유를 실제 장애 사례와 연결해, 공용 자원을 함께 사용해야 하는 이유와 행동 기준을 전달했다.
- 정량적 성과:
  - 공용 서버 2대의 사용·분산 기준을 문서화했다.
  - `/home` 계정별 기본 용량 기준을 최대 100GB로 명시했다.
  - 루트 파티션 여유 공간 목표를 300~400GB(약 20%)로 제시했다.
  - Milvus collection 로드 시 약 200GB RAM이 필요했던 실제 OOM 사례를 운영 기준에 반영했다.
  - RAM 점검, 시스템 정보, 디스크 사용량, GPU 사용자, 메모리 상위 프로세스, 계정 권한을 다루는 6종의 점검 스크립트를 제공했다.
- 정성적 성과:
  - 장애 대응 지식과 관리자 개인의 암묵지를 온보딩 자료로 전환해, 구성원이 같은 기준으로 서버를 사용하고 문제를 보고할 수 있는 기반을 만들었다.

## 배운 점

- 새롭게 배운 것:
  - AI 연구 서버 운영에서는 GPU뿐 아니라 시스템 RAM, CPU thread, 캐시·checkpoint가 위치한 파일시스템, 동시 세션 수가 모두 가용성과 연결된다.
  - “서비스가 멈췄다”는 현상만으로 Docker나 GPU를 원인으로 단정하지 않고, 메트릭과 프로세스·파일시스템 상태를 함께 확인해야 한다.
  - 운영 문서는 명령어 목록보다 “언제, 왜, 무엇을 확인하고, 문제가 보이면 누구에게 어떻게 공유할지”를 제공할 때 행동을 바꾼다.
- 부족했던 점:
  - 문서에 근거한 운영 기준은 마련했지만, 디스크·RAM·GPU 사용량을 시계열로 수집해 임계치 초과를 자동 알림하는 모니터링 체계는 별도로 구축하지 못했다.
  - 작업별 자원 예약·쿼터·스케줄링 체계가 없어, 대규모 작업의 충돌을 사용자 간 사전 공유에 주로 의존한다.
- 다음에 다르게 한다면:
  - Prometheus/Grafana 또는 동등한 도구로 CPU·RAM·GPU·디스크·세션 수를 모니터링하고, 디스크 80~90% 또는 메모리 임계치에서 알림을 설정하겠다.
  - Slurm 같은 스케줄러 또는 GPU 예약 정책을 도입해 장시간 학습과 Milvus 기동이 충돌하지 않도록 하겠다.
  - 신규 계정 생성 시 `/mnt` 디렉터리, `.bashrc`, 용량 확인 명령을 자동 적용하는 provisioning 스크립트를 만들겠다.
- 이후 다른 경험에 적용한 점:
  - 반복되는 운영 문의를 문서와 자동 점검 도구로 전환하는 방식, 그리고 실제 장애 사례를 예방 체크리스트로 바꾸는 방식을 다른 협업 환경의 온보딩과 운영 개선에도 적용할 수 있다.

## 자기소개서용 문장

### 문제 해결형

> 연구용 공용 서버에서 Milvus 재기동이 반복적으로 실패했을 때, Docker나 GPU 문제로 단정하지 않고 시스템 RAM·프로세스 상태를 함께 분석했습니다. collection 로드에 약 200GB RAM이 필요하고 동시 실험이 메모리를 점유해 OOM이 발생한 것을 확인한 뒤, CPU·RAM·GPU 통합 점검 체크리스트와 작업 전 공유 원칙을 만들었습니다. 이후 장애 대응 지식을 개인 경험에 머물게 하지 않고 온보딩 문서와 점검 스크립트로 표준화해, 구성원이 같은 기준으로 문제를 예방·보고할 수 있도록 했습니다.

### 협업형

> 여러 랩원이 GPU 학습과 벡터 DB를 함께 사용하는 환경에서, 서버 안정성은 관리자만의 문제가 아니라 사용자 모두의 사용 방식에 달려 있다고 판단했습니다. 그래서 `/home` 용량 제한, `/mnt` 기반 가상환경·캐시 경로, CPU thread 제한, 대규모 작업 사전 공유, 작업 후 프로세스 정리 규칙을 실제 장애 사례와 함께 문서화했습니다. 기술 정책의 이유와 실행 방법을 동시에 제공함으로써, 신규 랩원도 운영 원칙을 이해하고 공용 자원을 책임 있게 사용할 수 있는 협업 기반을 만들었습니다.

### 지원동기 또는 직무 역량형

> 저는 인프라 운영을 단순히 서버를 유지하는 일이 아니라, 사용자가 안전하게 연구·개발에 집중할 수 있는 환경을 설계하는 일로 이해합니다. Ubuntu 서버에서 SSH 계정, CUDA·PyTorch 환경, Docker 기반 Milvus, GPU·RAM·디스크 자원을 운영하며 실제 OOM과 디스크 포화 문제를 분석했습니다. 또한 이를 Bash 점검 도구와 재현 가능한 온보딩 문서로 전환한 경험을 바탕으로, 개발자 경험과 서비스 안정성을 함께 높이는 플랫폼·인프라 엔지니어가 되겠습니다.

## 면접 답변

### 예상 질문

- 가장 어려웠던 점은?
  - 장애 원인이 겉으로 보이는 Milvus·Docker·GPU가 아니라 시스템 RAM 부족과 동시 사용자 작업의 조합이었다는 점입니다. 단일 도구만 보지 않고 메모리, 프로세스, 디스크 상태를 함께 확인해 원인을 분리했습니다.
- 왜 이 방법을 선택했는가?
  - 공용 서버의 문제는 같은 유형으로 반복될 수 있습니다. 일회성 복구보다 사용자가 스스로 예방할 수 있도록 실제 사례, 점검 명령, 행동 규칙을 묶은 문서와 스크립트를 만드는 편이 확장 가능하다고 판단했습니다.
- 본인의 역할은 정확히 무엇이었는가?
  - 공용 서버 운영 지식과 장애 사례를 분석·정리하고, 계정·환경·저장공간·리소스·Milvus·하드웨어 점검 절차를 온보딩 문서와 Bash 도구로 표준화한 역할입니다. 권한 부여와 하드웨어 교체 같은 관리 권한 작업은 랩장·서버 관리자와 협업했습니다.
- 결과를 어떻게 측정했는가?
  - 문서상으로 서버 2대의 운영 기준, 계정당 100GB 기준, 루트 파티션 300~400GB 여유 목표, 약 200GB RAM OOM 사례를 명시했고, 반복 점검을 위한 6종 스크립트를 제공했습니다. 향후에는 문의·장애 건수와 리소스 시계열을 수집해 정량 측정을 보완하겠습니다.
- 다시 한다면 무엇을 개선할 것인가?
  - 현재는 사용자의 사전 점검과 공유에 의존하는 부분이 있으므로, 메트릭 수집·임계치 알림·GPU 예약/스케줄링·신규 계정 provisioning을 자동화하겠습니다.

### 1분 답변

> 랩실의 GPU 연구용 공용 Linux 서버를 운영하면서, 여러 사용자의 실험이 서로 영향을 주는 문제를 해결한 경험이 있습니다. 대표적으로 Milvus 재기동 실패가 발생했을 때 Docker나 GPU 문제로 보지 않고 `free`, `glances`, 프로세스 상태를 함께 확인해, collection 로드에 약 200GB RAM이 필요하고 동시 작업이 메모리를 점유해 발생한 OOM임을 파악했습니다. 또 `/home`에 쌓인 가상환경·캐시·checkpoint로 루트 파티션이 거의 가득 찬 사례를 분석해, `/mnt` 기반 저장 정책과 캐시·CPU thread 기본 설정을 만들었습니다. 이 내용을 SSH 접속, CUDA/PyTorch, Milvus, 리소스 점검까지 포함한 온보딩 문서로 정리하고, RAM·GPU·디스크·계정 권한을 확인하는 Bash 스크립트도 제공했습니다. 이 경험을 통해 장애를 복구하는 데서 끝나지 않고, 재발하지 않도록 사용자의 행동과 운영 절차를 설계하는 역량을 길렀습니다.
